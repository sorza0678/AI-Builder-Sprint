# AGENTS.md

## Project Context

이 프로젝트는 중고 매물의 링크를 입력해 가격 적정성, 물품 상태, 위험 신호, 거래 체크리스트를 제공하는 React Native 모바일 애플리케이션입니다.

기술 스택은 React Native, Expo, TypeScript입니다.

Figma 디자인을 기준으로 화면을 구현하며, 같은 저장소의 `backend/`에 실제 FastAPI 백엔드가 있습니다. 화면은 구현된 API 계약만 사용합니다. Mock 데이터는 서버가 제공하지 않는 영역에 한해 제한적으로만 씁니다.

## Expo Documentation

Expo 관련 코드를 작성하거나 설정을 변경하기 전에 반드시 아래의 정확한 버전 문서를 확인합니다.

[https://docs.expo.dev/versions/v54.0.0/](https://docs.expo.dev/versions/v54.0.0/)

다른 Expo 버전의 문서나 오래된 사용법을 기준으로 구현하지 않습니다.

## Repository Safety

모든 작업은 반드시 **포크된 저장소에서만** 수행합니다.

- 브랜치는 포크된 저장소에만 생성합니다.
- 커밋과 push는 포크된 저장소의 브랜치에만 수행합니다.
- Pull Request와 Issue는 포크된 저장소를 대상으로 생성합니다.
- 원본 parent 저장소에는 브랜치 생성, commit, push, Pull Request 생성, Issue 생성 등의 변경 작업을 하지 않습니다.
- 작업 전 `git remote -v`를 확인해 push 대상이 포크 저장소인지 검증합니다.
- 원본 저장소와 포크 저장소가 불분명하면 push하지 않습니다.

## Working Principles

1. 작업 전에 현재 프로젝트 구조, `package.json`, 기존 네비게이션, 스타일링 방식과 공통 컴포넌트를 확인합니다.
2. 기존 구조와 코딩 컨벤션을 우선하며 요구되지 않은 대규모 리팩터링을 하지 않습니다.
3. Figma 디자인을 최대한 정확하게 반영하되, 기존 기능과 화면 흐름을 불필요하게 변경하지 않습니다.
4. 작업 범위와 무관한 파일을 수정하거나 자동 포맷팅으로 프로젝트 전체를 변경하지 않습니다.
5. 기존 파일을 불필요하게 삭제하거나 이름을 변경하지 않습니다.
6. 이미 설치된 라이브러리와 공통 컴포넌트를 우선 사용합니다.
7. 새로운 패키지를 임의로 설치하지 않습니다. 패키지가 필요하면 설치하지 말고 필요 이유를 보고합니다.
8. 구현 범위를 벗어난 기능이나 백엔드 응답 구조를 추측해서 추가하지 않습니다.
9. 사용자 요청 없이 commit, push, Pull Request 또는 Issue를 생성하지 않습니다.

## Figma Implementation Rules

1. Figma의 레이아웃, 간격, 정렬, 크기, 타이포그래피, 색상과 컴포넌트 상태를 기준으로 구현합니다.
2. Figma 디자인과 기존 프로젝트 구조가 충돌하면 기존 구조를 유지하면서 최소 범위로 디자인을 반영합니다.
3. 임의의 장식, 화면, 버튼, 애니메이션 또는 기능을 추가하지 않습니다.
4. 반복되는 색상, 간격, 타이포그래피 값은 기존 theme 또는 design token을 재사용합니다.
5. 기존 token이 없다면 실제로 반복되는 값에 한해서만 최소한으로 분리합니다.
6. 한 화면에서만 사용하는 작은 UI를 불필요하게 전역 공통 컴포넌트로 만들지 않습니다.
7. 동일한 패턴이 여러 화면에서 반복될 때만 공통화를 고려합니다.
8. 고정된 특정 기기 크기에만 맞추지 말고 다양한 화면 크기와 안전 영역을 고려합니다.

## Navigation and Structure

1. 저장소에서 이미 사용하는 네비게이션 방식만 사용합니다.
2. Expo Router와 React Navigation을 동시에 도입하지 않습니다.
3. 기존 라우트와 파일 구조를 최소 변경으로 확장합니다.
4. 동일한 역할의 화면이나 경로를 중복 생성하지 않습니다.
5. 페이지 또는 화면 컴포넌트가 지나치게 커지면 기능 단위로 분리합니다.
6. 데이터 접근 로직과 표현 컴포넌트를 가능한 범위에서 분리합니다.

## Backend and Mock Boundaries

현재 저장소에는 실제 백엔드가 존재하며 프론트엔드는 구현된 API 계약만 사용합니다.

### 경로 제한

- `backend/**`는 읽기 전용 참조 영역입니다.
- `backend/**` 아래의 파일을 생성, 수정, 삭제, 이동하거나 포맷팅하지 않습니다.
- 수정 가능한 경로는 `frontend/**`뿐입니다.
- 백엔드 오류나 계약 불일치를 발견해도 직접 수정하지 않고 별도로 보고합니다.

### API 연결 원칙

- API 계약은 백엔드 문서보다 `backend/**`의 실제 구현을 우선합니다.
- 실제로 구현되지 않은 엔드포인트, 요청 필드, 응답 필드를 추측하지 않습니다.
- 모든 서버 요청은 `frontend/src/services/**`의 서비스 계층을 통해 처리합니다.
- 화면 컴포넌트에서 직접 `fetch`를 호출하지 않습니다.
- API의 snake_case DTO와 프론트 UI 모델을 분리하고 명시적인 adapter를 사용합니다.
- 서버 응답에 없는 정보를 Mock이나 임의 계산값으로 채우지 않습니다.
- 서버에서 제공하지 않는 기능은 `현재는 미지원하는 기능입니다.` 또는 `지원 예정`으로 표시합니다.
- API 응답과 Mock 데이터를 하나의 화면 결과에 혼합하지 않습니다.

### 인증 경계

- 백엔드는 비밀번호 해시(PBKDF2)와 Bearer 토큰 기반 인증을 제공합니다. `POST /api/v1/auth/signup`, `POST /api/v1/auth/login`을 사용합니다.
- 발급받은 토큰과 세션은 기기의 AsyncStorage에 저장합니다 (`src/storage/auth-session-storage.ts`).
- 토큰을 임의로 만들지 않습니다. 서버가 발급한 값만 그대로 보관하고 전송합니다.
- 로그인 이후 API의 `user_id`에는 현재 로그인 계정 ID를 사용합니다. 비회원 상태에서는 기기별 `guest-*` ID를 씁니다 (`src/storage/guest-id-storage.ts`).
- 비회원 기록을 계정으로 옮길 때는 `POST /api/v1/account/migrate-guest`를 사용합니다. 토큰이 필요하며 여러 번 호출해도 안전합니다.
- 비밀번호는 화면에서 다루는 즉시 서버로 보내고 따로 저장하지 않습니다.

### 외부 서비스 경계

- 프론트에서 Upstage API를 직접 호출하지 않습니다.
- Upstage API key를 프론트 코드, Expo 환경변수 또는 앱 번들에 저장하지 않습니다.
- 크롤링, AI 분석, 시세 계산 및 위험 판정은 백엔드 책임입니다.
- 프론트는 백엔드가 반환한 분석 결과만 표시합니다.

### Mock 데이터 원칙

기존 Mock 데이터는 현재 화면이 직접 의존하고 있을 때만 유지합니다.

새로운 Mock 데이터가 필요한 경우:

- 화면 컴포넌트 내부에 대량의 Mock 데이터를 작성하지 않습니다.
- `frontend/src/mocks/**` 또는 기존 서비스 계층에 분리합니다.
- 실제 API가 이미 지원하는 영역에는 새로운 Mock을 추가하지 않습니다.
- 아직 확정되지 않은 백엔드 응답 형식을 과도하게 설계하지 않습니다.
- Mock 데이터는 실제 서버 데이터와 동시에 표시하지 않습니다.
- API로 교체할 위치에는 구체적인 TODO를 남깁니다.

### UI 보호 원칙

- 백엔드 연결을 위해 기존 Figma 디자인을 임의로 변경하지 않습니다.
- 데이터가 부족한 경우에도 전체 화면을 임시 UI로 교체하지 않습니다.
- 기존 디자인 구조를 유지하고, 해당 데이터 영역에만 미지원 상태를 표시합니다.
- loading, empty, error, retry 상태를 기존 디자인 안에서 처리합니다.

## TypeScript and React Native Rules

1. `any`, `@ts-ignore` 또는 불필요한 type assertion으로 타입 오류를 숨기지 않습니다.
2. 컴포넌트 Props와 주요 데이터 구조의 타입을 명시합니다.
3. nullable 또는 optional 값은 화면에서 안전하게 처리합니다.
4. HTML 태그, CSS 파일, DOM API 등 웹 전용 코드를 사용하지 않습니다.
5. React Native 기본 컴포넌트 또는 기존 설치 라이브러리를 사용합니다.
6. 긴 화면은 적절한 `ScrollView` 또는 `FlatList`로 처리하며 불필요한 중첩 스크롤을 피합니다.
7. 키보드, 안전 영역, 터치 영역과 이미지 로드 실패를 고려합니다.
8. 지원되지 않는 React Native 스타일 속성을 사용하지 않습니다.
9. 최종 코드에 디버깅용 `console.log`를 남기지 않습니다.

## Expo Feature Rules

클립보드, 이미지 선택, 바텀시트 등의 기능은 프로젝트에 이미 설치된 패키지를 우선 사용합니다.

- 필요한 Expo 패키지가 설치되어 있는지 먼저 확인합니다.
- 설치되어 있지 않으면 임의로 설치하지 않습니다.
- 설치가 필요한 경우 기능을 추측해서 우회 구현하지 말고 필요한 패키지와 이유를 보고합니다.
- 권한 거부, 사용자 취소와 실행 실패를 안전하게 처리합니다.
- 기존 바텀시트 라이브러리가 없다면 새 패키지를 추가하기 전에 React Native 기본 `Modal`로 구현 가능한지 검토합니다.

## Validation

작업 완료 전 `package.json`에 정의된 명령을 우선 사용하여 가능한 검사를 실행합니다.

최소 확인 항목:

- TypeScript 타입 검사
- lint
- 사용하지 않는 import
- 잘못되거나 중복된 라우트
- 웹 전용 코드 사용 여부
- 신규 패키지 또는 잠금 파일 변경 여부
- 작업 범위 밖의 파일 변경 여부
- 디버깅용 로그 잔존 여부

검사를 실행하지 못했거나 기존 오류로 실패한 경우 숨기지 말고 정확한 원인을 보고합니다.

## 작업 전 자가 점검

새 작업을 시작하기 전에 이 문서를 다시 읽고 아래를 확인합니다.

- Expo SDK 54 기준으로 구현했는지 (v54 공식 문서를 확인했는지)
- Figma 디자인을 반영하면서 기존 구조와 네비게이션 방식을 유지했는지
- 백엔드 API, 인증 방식, 응답 구조를 임의로 추측하지 않았는지
- 웹 전용 코드나 React Native에서 지원하지 않는 스타일을 쓰지 않았는지
- 새 패키지를 임의로 설치하거나 잠금 파일을 불필요하게 바꾸지 않았는지
- 작업 범위와 무관한 파일을 건드리지 않았는지
- `any`, `@ts-ignore`, 디버깅용 `console.log`가 남아 있지 않은지
- `git remote`와 현재 브랜치를 확인했고 모든 변경이 포크 저장소에만 적용되는지

이 문서와 충돌하는 변경이 있다면 이 문서를 기준으로 최소 범위에서 되돌린 뒤 작업을 이어갑니다.
